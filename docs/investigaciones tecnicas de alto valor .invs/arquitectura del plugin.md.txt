Gestión de Dependencias MultinivelPara asegurar la robustez en entornos heterogéneos, FreeCAD evalúa tres niveles complementarios de declaración de dependencias:El primer nivel corresponde al archivo package.xml, el cual gestiona la jerarquía de módulos internos de FreeCAD o de otros complementos (Workbenches) requeridos para la ejecución, permitiendo declarar formalmente la necesidad del entorno BIM o de complementos auxiliares de modelado. El segundo nivel se gestiona mediante el archivo metadata.txt, en el cual se especifican dependencias de bibliotecas de Python del sistema o facultativas mediante las claves pylibs= y optionalpylibs=. Por último, el tercer nivel emplea un archivo requirements.txt o pyproject.toml para definir paquetes del ecosistema PyPI (como numpy o scipy), permitiendo que el Addon Manager utilice la herramienta pip en un entorno aislado durante el proceso de instalación.Estructura Canónica de DirectoriosEl paso de un repositorio plano a un espacio de nombres (namespace) profesional requiere organizar el código fuente distinguiendo estrictamente la lógica de datos, la representación visual y los recursos de interfaz.Ruta de Archivo o DirectorioRol Arquitectónico y PropósitoÁmbito de Cargapackage.xmlManifiesto de metadatos del complemento para el Addon Manager.Global / Instalaciónmetadata.txt / requirements.txtDeclaración de dependencias de Python y de otros complementos.Entorno de EjecuciónInit.pyPunto de entrada de bajo nivel. Esta diferenciación impone una arquitectura de inicialización dividida en dos fases secuenciales.Durante el arranque general de FreeCAD, el sistema escanea el directorio de módulos /Mod/ e invoca el archivo Init.py de cada complemento. Este archivo se ejecuta siempre, independientemente de si la aplicación se inicia en interfaz gráfica o en modo de línea de comandos sin cabecera (headless) para automatización de procesos en servidor. En consecuencia, la responsabilidad de Init.py debe reducirse estrictamente a registrar clases de datos, asociar tipos de archivo o extensiones de importación/exportación mediante FreeCAD.addImportType() y FreeCAD.addExportType(), e inicializar variables del árbol de parámetros globales (App.ParamGet). La inclusión de importaciones relativas a paquetes de interfaz gráfica como FreeCADGui, PySide o pivy dentro de Init.py genera fallos catastróficos en entornos de ejecuciones automatizadas, rompiendo la compatibilidad con herramientas de CI/CD y automatización industrial.Si FreeCAD se inicia con la interfaz gráfica activa, el sistema verifica que la variable FreeCAD.GuiUp sea verdadera e invoca inmediatamente después el archivo InitGui.py. import FreeCAD
import FreeCADGui

class GabineteTaskPanel:
    """Panel de tareas alojado en la vista lateral de FreeCAD."""

    def __init__(self):
        self.form = QtWidgets.QWidget()
        self.form.setWindowTitle("Parámetros del Gabinete")

        layout = QtWidgets.QVBoxLayout(self.form)

        self.spin_ancho = QtWidgets.QDoubleSpinBox()
        self.spin_ancho.setRange(100.0, 3000.0)
        self.spin_ancho.setValue(600.0)
        self.spin_ancho.setSuffix(" mm")

        layout.addWidget(QtWidgets.QLabel("Ancho del Módulo:"))
        layout.addWidget(self.spin_ancho)

    def accept(self):
        """Se ejecuta al presionar el botón 'OK' nativo del panel de tareas."""
        doc = FreeCAD.ActiveDocument
        doc.openTransaction("Crear Gabinete Paramétrico")

        obj = doc.addObject("Part::FeaturePython", "GabineteParametrico")
        from freecad.carpinteria.objects.gabinete import GabineteProxy
        from freecad.carpinteria.views.view_gabinete import ViewProviderGabinete

        GabineteProxy(obj, self.spin_ancho.value())
        ViewProviderGabinete(obj.ViewObject)

        doc.commitTransaction()
        doc.recompute()
        FreeCADGui.Control.closeDialog()
        return True

    def reject(self):
        """Se ejecuta al presionar 'Cancelar' o la tecla Escape."""
        FreeCADGui.Control.closeDialog()
        return True

Estrategias de Integración: Workbench Independiente vs. Módulo Adicional en BIMAl abordar la arquitectura de la herramienta para el flujo de trabajo edilicio o de diseño de interiores, surge el dilema de definir si el módulo debe implementarse como un Workbench independiente o como un complemento que dependa y se ejecute estrictamente dentro del Workbench BIM de FreeCAD.Análisis comparativo de los enfoques arquitectónicos:En el enfoque de Workbench Independiente, la herramienta dispone de su propio espacio de trabajo en el menú principal de selección de entornos. Esta alternativa ofrece la máxima autonomía de código, manteniendo el desarrollo completamente desacoplado de las actualizaciones internas del entorno BIM. No obstante, genera cierta fricción en el usuario final si este necesita conmutar constantemente de Workbench para intercalar la modelación de muros con la colocación de mobiliario paramétrico.En el enfoque de Módulo Adicional Estricto de BIM, la extensión no registra un espacio de trabajo propio, sino que inyecta sus comandos directamente dentro de los menús y barras del Workbench BIM. Aunque esto resulta conveniente para proyectistas que operan exclusivamente en BIM, introduce un acoplamiento rígido hacia la API del módulo BIM, exponiendo el plugin a fallos en caso de reestructuraciones del código base del entorno primario.La Arquitectura Híbrida Autónoma representa la solución técnica más avanzada y elegante. En este esquema, el complemento se empaqueta e instala como un Workbench totalmente independiente, garantizando su funcionamiento en cualquier instalación de FreeCAD. No obstante, durante la inicialización visual (InitGui.py), el módulo ejecuta un proceso de detección pasiva: si el Workbench BIM está instalado y cargado en memoria, inyecta dinámicamente sus barras de herramientas y menús dentro de la interfaz de BIM sin alterar el árbol de dependencias central.Criterio TéchnicoWorkbench IndependienteMódulo Adicional de BIMArquitectura Híbrida Autónoma (Recomendada)Aislamiento de CódigoAbsoluto. Despliegue, Distribución y Gestión de Entrega EmpresarialEl empaquetado estandarizado permite desplegar el Workbench tanto en la comunidad global de software libre como en infraestructuras corporativas cerradas bajo normativas de auditoría interna.Publicación Oficial en el FreeCAD Addon ManagerPara poner el módulo a disposición de la comunidad internacional a través del Gestor de Complementos oficial de FreeCAD, el flujo de publicación requiere los siguientes pasos:Verificación de Metadatos: Validar la integridad del manifiesto package.xml mediante las Herramientas de Desarrollador del Addon Manager (Tools -> Addon Manager -> Developer Tools).Alojamiento en Repositorio Público: Publicar el código fuente en un servicio Git accesible (GitHub, GitLab, Framagit o Salsa Debian) garantizando el etiquetado correcto de versiones semánticas.Solicitud de Inclusión (Pull Request): Realizar una bifurcación (fork) del repositorio de índice oficial FreeCAD/FreeCAD-addons e incluir el nuevo módulo como un submódulo de Git en el archivo .gitmodules, asegurando su ordenación alfabética.Inspección Automatizada: El pipeline de integración continua del proyecto FreeCAD verificará la sintaxis del archivo package.xml, la validez de la licencia informada y la ausencia de conflictos en la estructura de rutas.Despliegue en Entornos Corporativos PrivadosEn entornos industriales donde el software debe distribuirse en redes locales sin acceso a Internet o protegiendo algoritmos propietarios, se deben utilizar las siguientes metodologías de despliegue:A partir de la versión 0.21, FreeCAD admite la configuración de repositorios Git personalizados dentro de las preferencias del Addon Manager (Edit -> Preferences -> Addon Manager -> Custom Repositories). Esto permite a los administradores de sistemas apuntar el cliente de FreeCAD a un servidor GitLab o GitHub Enterprise interno, gestionando actualizaciones automáticas dentro del perímetro de seguridad de la empresa. Alternativamente, las empresas pueden automatizar el despliegue mediante Directivas de Grupo (GPO) o scripts de configuración, copiando la carpeta del módulo empaquetado directamente en la ruta del sistema correspondiente:Entornos Windows: %APPDATA%\FreeCAD\Mod\CarpinteriaParametrica\Entornos Linux: ~/.local/share/FreeCAD/Mod/CarpinteriaParametrica/Entornos macOS: ~/Library/Application Support/FreeCAD/Mod/CarpinteriaParametrica/Conclusiones y Recomendaciones de IngenieríaAdopción del Estándar package.xml: Es indispensable sustituir la colección de scripts aislados por la estructura de paquetes oficial centrada en el manifiesto package.xml en la raíz del proyecto. Esto garantiza la correcta lectura de metadatos, iconos y dependencias por parte de FreeCAD.Desacoplamiento entre Modelo e Interfaz: La lógica de negocio y modelado geométrico debe aislarse en clases Proxy Part::FeaturePython dentro de Init.py o submódulos del núcleo de aplicación, restringiendo el uso de FreeCADGui, PySide y gráficos Coin3D a los archivos de vista (ViewProvider) y a la inicialización visual de InitGui.py.Estandarización de Interfaces con Task Panels: Se debe abandonar la implementación de diálogos emergentes flotantes y estandarizar la creación de herramientas mediante FreeCADGui.Control.showDialog(), garantizando la integración nativa del flujo de trabajo en la pestaña lateral de tareas de FreeCAD.Implementación de Arquitectura Híbrida: La solución más robusta y elegante consiste en registrar el desarrollo como un Workbench totalmente independiente, agregando una rutina de detección que inyecte sus herramientas en el Workbench BIM cuando este se encuentre activo. Esto proporciona máxima flexibilidad operativa y protege al módulo frente a cambios en APIs de terceros.
